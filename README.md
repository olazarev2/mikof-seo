# SEO-техдолг mikof.md

Техническое задание для разработчика сайта клиники **mikof.md** и инструмент независимой приёмки работ.

| **Задачи и прогресс** | [Issues](../../issues) · [Milestone «SEO-техдолг 2026-09»](../../milestone/1) |

| **Источник правды** | [`docs/tz-dev-2026-09.md`](docs/tz-dev-2026-09.md) |

Аудит проведён 3 сентября 2026 года методом внешнего сканирования: HTTP-заголовки, исходный HTML, отрендеренный DOM, sitemap, robots — главная, 13 разделов, 49 страниц услуг, 17 карточек врачей, три языковые версии. Доступа к исходному коду сайта не было, поэтому все дефекты сформулированы как воспроизводимые проверки, а не как правки конкретных файлов.

## Что не так с сайтом коротко

1. **Сайт существует в двух полных копиях** — `www.mikof.md` отдаёт 200 без редиректа и canonical на себя. Google индексирует именно www-версию, вес делится пополам.
2. **Прайс невидим для поиска** — цены подгружает Livewire после выбора города. В HTML `prices.shtml` два вхождения слова «lei». Для AI-краулеров, которые не исполняют JavaScript, прайса клиники не существует.
3. **Sitemap заявляет 94 URL из ~320**, в robots.txt нет директивы `Sitemap:`, `<h1>` нет на 83 страницах, JSON-LD нет ни на одной.

## Порядок работ

Блоки идут по убыванию отдачи и связаны зависимостями — начинать строго с A.

| Блок | Приоритет | Задачи | О чём | Оценка |
|---|---|---|---|---|
| **A** | P0 | A1–A7 | Технический фундамент: www, цены в HTML, h1, hreflang, sitemap, description, title | 1–2 дня, даёт основной эффект |
| **B** | P1 | B1–B6 | Разметка и представление: JSON-LD, скорость, Open Graph, крошки, дубли, NAP | после A |
| **C** | P2 | C1–C5 | Структура и AI-видимость: ЧПУ, E-E-A-T, llms.txt, перелинковка, VisuMax | после B |
| **D** | P3 | D1–D4 | Измеримость и гигиена: аналитика, локализация мелочей, орфография, кеш | параллельно, фоном |

Перед стартом нужны ответы заказчика — см. issue [«Вопросы к заказчику до старта работ»](../../issues?q=is%3Aissue+label%3Aask). Без них нельзя закрыть B1 (координаты для `geo`), B6 (реальные часы работы), C1 (решение по ЧПУ), C5 (решение по `/visumax`), C4 (привязка врачей к услугам).

## Как это устроено

```
docs/       ТЗ и данные аудита — источник правды
site/       веб-версия ТЗ, разворачивается на Vercel
verify/     скрипт приёмки + история отчётов
tools/      нарезка ТЗ на issues (служебное)
```

Каждая из 22 задач заведена отдельным issue с тем же текстом, что и в ТЗ, плюс командой проверки. Прогресс виден в milestone: закрытые задачи / всего.

## Работа исполнителя

1. Взять issue из блока A, назначить на себя.
2. Сделать по описанию — в задаче есть готовые значения, конфиги и код, изобретать ничего не нужно.
3. Прогнать проверку своей задачи: `node verify/verify.mjs --only A1`.
4. Закрывать issue, когда проверка даёт **PASS**. FAIL означает, что на боевом сайте изменение не видно.

## Приёмка со стороны заказчика

Полный прогон в любой момент, независимо от отчётов исполнителя:

```powershell
cd mikof-seo
.\verify\Verify-Seo.ps1          # или: node verify/verify.mjs
```

Скрипт обращается к живому сайту и печатает по каждой из 22 задач PASS / FAIL / WARN, а внизу — «Выполнено N из 22». Отчёт с деталями сохраняется в `verify/reports/ГГГГ-ММ-ДД.md`, отчёты коммитятся — так видно, что и когда реально появилось на сайте.

Три вещи скрипт проверить не может, они делаются глазами: Google Rich Results Test (нет открытого API), настройка целей GA4 и Search Console (только в аккаунтах), полнота карты редиректов по всем 49 услугам (проверяются три образца).
